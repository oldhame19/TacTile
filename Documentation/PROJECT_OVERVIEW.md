# TacTile — Project Overview

## 1. Game Concept and Objectives

**TacTile** is a digital, two-player turn-based tactical board game developed in Unity. The game merges spatial grid control (reminiscent of *Othello* / *Reversi*) with numerical edge-combat mechanics (inspired by card-battlers such as *Triple Triad* and tactical games like *Stratego*).

Two players—**Player 1** (White) and **Player 2** (Black)—alternate placing numbered, color-coded tiles onto a shared grid. When a newly placed tile borders opponent tiles, cardinal edge strengths are compared. If the attacking edge strength exceeds the defending edge strength, the opponent's tile is captured and flips ownership to the attacker.

### Primary Objective
The objective of the game is to control the majority of placed tiles on the board when all playable board spaces are filled or no legal actions remain.

## 2. Core Gameplay Rules and Mechanics

### Board Dimensions and Configuration
- **Grid Size:** $5 \times 5$ square grid ($25$ total spaces), generated dynamically at runtime by [BoardGenerator.cs](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Board/BoardGenerator.cs).
- **Center Space:** The exact center space at coordinate `[2, 2]` is a fully playable space, permanently assigned as a **Neutral Boost Space** (colored purple).
- **Colored Boost Spaces:** Exactly $6$ colored boost spaces are randomly distributed across the remaining $24$ spaces ($2$ Red, $2$ Light Blue, $2$ Yellow).
- **Standard Spaces:** The remaining $18$ spaces are standard board squares with no modifiers.

```
       Column 0    Column 1    Column 2    Column 3    Column 4
Row 4 [ Standard ][  Boost   ][ Standard ][ Standard ][  Boost   ]
Row 3 [ Standard ][ Standard ][  Boost   ][ Standard ][ Standard ]
Row 2 [ Standard ][  Boost   ][ NEUTRAL  ][ Standard ][  Boost   ]
Row 1 [ Standard ][ Standard ][ Standard ][  Boost   ][ Standard ]
Row 0 [  Boost   ][ Standard ][ Standard ][ Standard ][ Standard ]
```
*(Note: Colored boost locations vary each match due to Fisher-Yates randomization.)*

### Player Tile Counts & Intentional Design Decision
- **Starting Allocation:** Each player receives **13 tiles**, spawned in racks outside the board (Player 1 at $Z = -7.3$, Player 2 at $Z = 7.3$).
- **Total Tiles in Game:** $26$ tiles ($13$ for Player 1, $13$ for Player 2).
- **Intentional Design Decision:** Each player receives 13 tiles. The board contains 25 playable spaces, including the center neutral purple boost space. Therefore, when the board is full, exactly one tile remains unused overall. Which player retains that tile depends on placement order.

### Tile Generation and Characteristics
Each tile is procedurally generated at the start of the match by [TileGenerator.cs](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Tile/TileGenerator.cs) under constraints configured in [GameBalanceConfig.asset](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Config/GameBalanceConfig.asset):
1. **Side Strengths:** Four integer strengths representing edges: **Top**, **Right**, **Bottom**, and **Left**. Each edge strength ranges from $0$ to $4$.
2. **Tick Budget:** The sum of all four edges on any given tile is constrained to a range of $7$ to $9$ total ticks:
   $$\text{minimumTotalTicks (7)} \le (\text{Top} + \text{Right} + \text{Bottom} + \text{Left}) \le \text{maximumTotalTicks (9)}$$
3. **Tick Color:** Every tick on a given tile shares a single color (`Red`, `LightBlue`, or `Yellow`).
4. **Color Distribution:** Player racks receive a balanced distribution across the three colors generated by [TileSpawner.cs](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Tile/TileSpawner.cs#L99-L126).

## 3. Combat, Capture, and Scoring Rules

### Combat Mechanics
Combat triggers immediately when a player places a tile on an empty board space via [GameDriver.ResolveCaptures()](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Game/GameDriver.cs#L198-L240). The placed tile initiates combat against all immediately adjacent, orthogonal opposing tiles:
- **Top Neighbor `[Row + 1, Col]`:** Attacker `Top` strength vs. Defender `Bottom` strength.
- **Right Neighbor `[Row, Col + 1]`:** Attacker `Right` strength vs. Defender `Left` strength.
- **Bottom Neighbor `[Row - 1, Col]`:** Attacker `Bottom` strength vs. Defender `Top` strength.
- **Left Neighbor `[Row, Col - 1]`:** Attacker `Left` strength vs. Defender `Right` strength.

### Boost Bonuses
Effective strength is computed by [GameDriver.GetEffectiveStrength()](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Game/GameDriver.cs#L305-L376):
- **Base Strength:** The tick count on the relevant edge ($0$ to $4$).
- **Neutral Center Boost:** Grants $+1$ strength (`neutralBoostBonus`) to all sides of any tile on the space, regardless of tick color.
- **Matching Color Boost:** Grants $+1$ strength (`matchingColorBoostBonus`) to all sides **only if** the occupying tile's tick color matches the boost space color (`Red`, `LightBlue`, or `Yellow`).
- **Defending Tiles:** Defending tiles also receive boost bonuses if currently resting on a boost space.

### Capture Resolution
- **Strict Greater-Than Rule:** A capture occurs if and only if:
  $$\text{Effective Strength}_{\text{Attacker}} > \text{Effective Strength}_{\text{Defender}}$$
- **Ties Favor the Defender:** If the strengths are equal, no capture occurs.
- **Ownership Flip:** When captured, the defending tile's owner is updated to the attacker, and its material instantly recolors via [TileView.SetOwner()](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Tile/TileView.cs#L36-L40).
- **Single-Step Combat:** Captures do not trigger cascades or chain reactions; only the actively placed tile attacks adjacent tiles.

### Scoring
- The live score is displayed by [ScoreboardUI.cs](file:///C:/Users/oldha/OneDrive/Documents/CST-410/TacTile/Assets/Scripts/Game/ScoreboardUI.cs).
- Each placed tile controlled by a player contributes exactly **$1$ point**. Unplaced tiles in player racks do not contribute to the score.
- As tiles are captured back and forth, the scores dynamically reflect the number of controlled board tiles.

## 5. Intentional Design Decisions and Known Limitations

### Intentional Decisions
1. **Board Size (5x5):** The 25-space grid provides an odd number of total spaces, ensuring an odd number of placed tiles at full capacity, which prevents an exact tie in tile count if all 25 spaces are occupied.
2. **Tile Count (13 per player):** Each player receives 13 tiles. The board contains 25 playable spaces, including the center neutral purple boost space. Therefore, when the board is full, exactly one tile remains unused overall. Which player retains that tile depends on placement order.
3. **Local Combat:** Captures do not trigger chain flips, keeping gameplay deterministic, transparent, and easy to calculate mentally for players.

### Current Gaps & Required Additions (Before University Submission)
1. **Missing Game-Over Sequence & Victory Screen:** `GameState.IsGameOver` is not evaluated in `GameDriver`. The required Fleshed-Out Victory Screen must be implemented with winner announcement, scores, "Play Again", and "Return to Menu".
2. **Missing Main Menu & Settings Interface:** Players cannot access rules or customize balance variables without opening the Unity Inspector. The required Main Menu, Rules, and Settings system must be built with joint tick validation.
3. **Missing Boost Visual Cues:** Boost calculations occur entirely in code without visual indication on the boosted tile.
4. **Console-Only Move Validation Feedback:** Illegal actions log warnings to `Debug.Log` rather than giving in-game feedback.
5. **Desktop Click Input Only:** Relies on 3D BoxCollider `OnMouseDown()` events (sufficient for desktop deliverable; mobile gesture enhancements deferred to Phase 2).
